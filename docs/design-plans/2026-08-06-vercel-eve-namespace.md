# Vercel Eve Namespace (`@arcjet/guard/vercel-eve/v0`) Design

## Summary

This design adds the second vendor namespace to `@arcjet/guard`:
`@arcjet/guard/vercel-eve/v0`, integrating Vercel's Eve agent framework. It is
the first real test of the subpath convention settled in
[the guard SDK subpath namespaces ADR](../../../arcjet/docs/adrs/2026-07-28-guard-sdk-subpath-namespaces.md),
and it confirms that ADR's prediction: the surface diverges from
`vercel-ai/v7` by more than a changed signature. Eve is filesystem-first with
no author-controlled call site, its hooks are observe-only and cannot reject a
turn, its model-facing tools frequently come from *connections* rather than
authored tool files, and correlation must be derived from a durable session id
rather than generated by a caller. The `toolsContext` fan-out that
`aiToolsContext` exists for has no analogue at all.

What Eve does give is a gate the AI SDK lacks: the `approval` field, present on
authored tools **and** on OpenAPI and MCP connections, which returns a status
carrying a `reason` string the model reads. That is the widest enforcement
surface in the framework, and it is the centrepiece of this namespace. Around
it sit three more helpers: `guardInbound` for the channel boundary (the only
place a turn can be declined before it starts), `guardTool` for authored tool
files whose `execute` we can wrap, and `arcjetHooks` for observe-only capture
of the lifecycle events that carry execution outcomes. The agnostic layer
(`createAgentContext`, `guardAction`, `captureAction`, `securityMetadata`,
`ArcjetDeniedError`, `ArcjetGuardUnavailableError`) is proxy re-exported
unchanged, exactly as `vercel-ai/v7` does it.

The namespace is typed against `eve` with **type-only imports**: no module in
`src/vercel-eve/v0/` imports `eve` at runtime. That is not stylistic. `eve`
declares `engines.node: ">=24"` while `@arcjet/guard` supports Node 22 and runs
its unit-test matrix on 22, 24 and 26; a runtime import would either drag a
3,000-file dependency into every test run or cut the matrix down to Node 24.
Type-only coupling keeps the peer optional in the strongest sense — the tests
construct plain objects and never load Eve at all.

Delivery is eight phases: namespace scaffolding, session-derived correlation
(with a small shared extraction from `vercel-ai/v7`), the approval gate, the
tool wrapper and inbound screen, hook capture, example and documentation, the
dogfood integration of `arcjet/apps/toto`, and full verification.

## Definition of Done

### Deliverables

1. **`@arcjet/guard/vercel-eve/v0`** subpath export shipping `guardApproval`,
   `guardInbound`, `guardTool`, `arcjetHooks`, `eveAgentContext`, and proxy
   re-exports of the agnostic layer.
2. **`eve` as an optional peer dependency** (`>=0.30 <1`), with no runtime
   import anywhere in the namespace.
3. **Example app** under `examples/` showing an Eve agent with a guarded
   connection, a guarded authored tool, a screened channel, and hook capture.
4. **Integration skill** so a coding agent can perform the Eve integration.
5. **Documentation**: `arcjet-guard/README.md` namespace section extended; the
   ADR's `vercel-eve/v1` naming corrected to `v0` with the reasoning recorded.
6. **Dogfood proof**: `arcjet/apps/toto` migrated onto the helpers, its
   hand-rolled channel screening replaced, and one Slack conversation producing
   guard decisions and capture events joined into a single Sequence.

### Success criteria

- A developer (or coding agent) can guard an Eve agent's connection tools,
  authored tools, and inbound channel with the same conceptual vocabulary they
  would use for the Vercel AI SDK, without learning a second product.
- One toto conversation reconstructs end to end in the Arcjet Console: the
  channel screening decision, each tool-gate decision, and the execution
  outcome of each tool call.
- Adding this namespace requires only **two** deliberate, tested changes to
  `src/agents/` — the `retryAfterSeconds` extraction and exporting the
  correlation-id validation predicate that `context.ts` keeps private today —
  and no change to the build config.

### Out of scope

- Publishing the agnostic layer at the root export. This namespace is the
  evidence the ADR wanted before that decision; making it is a follow-up.
- An Eve *extension* package (`@arcjet/eve-extension`) that mounts the hooks
  and gates automatically. Recorded as future work in Additional
  Considerations.
- Guarding sandbox command execution (`eve/sandbox`). No enforcement point has
  been identified there; noted as an open question.
- OTel span ingestion. Eve's `defineInstrumentation` is a plausible future
  carrier and this design stays compatible with it.
- `vercel-eve/v1`. Added additively when `eve` reaches 1.0.

## Acceptance Criteria

### vercel-eve-namespace.AC1: The subpath resolves as specified

- **vercel-eve-namespace.AC1.1 Success:** `import { guardApproval, guardInbound, guardTool, arcjetHooks, eveAgentContext } from "@arcjet/guard/vercel-eve/v0"` resolves.
- **vercel-eve-namespace.AC1.2 Success:** The namespace re-exports the agnostic layer, and each proxied export is the *same function identity* as the one `@arcjet/guard/vercel-ai/v7` exports. Both namespaces proxy one implementation; two identities would mean a second copy to keep in sync.
- **vercel-eve-namespace.AC1.3 Failure:** `@arcjet/guard/vercel-eve` (unversioned), `@arcjet/guard/vercel-eve/v1` (a major that does not exist yet), and deep paths such as `@arcjet/guard/vercel-eve/v0/guard-approval` do not resolve.
- **vercel-eve-namespace.AC1.4 Success:** The root export surface is unchanged: the export map keys are exactly `.`, `./bun`, `./fetch`, `./node`, `./vercel-ai/v7`, `./vercel-eve/v0`, and the `.` entry's runtime conditions are unchanged. `./agents` is still absent.
- **vercel-eve-namespace.AC1.5 Success:** `eve` appears in `peerDependencies` as `>=0.30 <1` and is marked optional in `peerDependenciesMeta`; installing a project that depends on `@arcjet/guard` without Eve produces no peer warning or error.

### vercel-eve-namespace.AC2: The namespace never imports Eve at runtime

- **vercel-eve-namespace.AC2.1 Success:** Every `eve` (and `eve/*`) import in `src/vercel-eve/v0/**` is type-only — written `import type` or `export type`. A value import of `eve` anywhere in the subtree fails this criterion. Asserted by a static scan over source, in the style of the existing agnostic-layer import-graph test.
- **vercel-eve-namespace.AC2.2 Success:** The unit-test suite for the namespace passes on Node 22, 24 and 26, with `eve` absent from `node_modules`. This is what AC2.1 buys and is the reason it is a criterion rather than a preference — Eve declares `engines.node: ">=24"`.
- **vercel-eve-namespace.AC2.3 Success:** Nothing reachable from `src/agents/index.ts` imports `eve` or `ai`. The existing agnostic-boundary test is extended to name `eve`, not merely left to cover `ai`.

### vercel-eve-namespace.AC3: Correlation is session-derived

- **vercel-eve-namespace.AC3.1 Success:** `eveAgentContext(ctx)` given a context whose `session.parent` is absent returns an `ArcjetAgentContext` whose `correlationId` is `ctx.session.id`.
- **vercel-eve-namespace.AC3.2 Success:** Given a context whose `session.parent` is present, the `correlationId` is `ctx.session.parent.rootSessionId`, **not** `ctx.session.id`. A subagent's decisions must land on the user-facing session's Sequence rather than a Sequence nobody looks at.
- **vercel-eve-namespace.AC3.3 Edge:** Given a session id that `createAgentContext` would reject (empty, over 256 characters, or containing non-printable characters), `eveAgentContext` does **not** throw. It falls back to a generated ULID, emits a warning gated on `ARCJET_LOG_LEVEL`, and records the rejected value under metadata key `eve.session`. A helper that runs inside a model-driven tool call must never be the reason the call fails.
- **vercel-eve-namespace.AC3.4 Success:** The returned metadata carries `user` set from `ctx.session.auth.current.principalId` when a current principal exists, and omits `user` entirely when `auth.current` is `null`. No empty-string key.
- **vercel-eve-namespace.AC3.5 Success:** The returned metadata carries `eve.session` (the session id) and `eve.turn` (`ctx.session.turn.id`), and carries `eve.parent-session` only for delegated sessions. Caller-supplied metadata is merged **over** these, so an explicit value wins.
- **vercel-eve-namespace.AC3.6 Success:** Every derived metadata key uses only letters, digits, `-`, `.` and `_` — the character class the server enforces, documented in the `@arcjet/guard` README's Metadata section — asserted against that class explicitly, **and** survives a round trip through `encodeMetadata` with no `AJ1017` warning. The second half is a smoke test, not the proof: `arcjet-guard/src/metadata.ts` states that key-name validity is enforced **server-side** (the limits are per-account configurable), and the SDK encoder drops a key only for a lone surrogate or a value `JSON.stringify` cannot represent. So the round trip cannot fail on a key name, and a criterion resting on it alone would be vacuous. The character-class assertion is the load-bearing half.

### vercel-eve-namespace.AC4: `guardApproval` gates tool and connection calls

- **vercel-eve-namespace.AC4.1 Success:** On ALLOW the returned `Approval` resolves to `"not-applicable"` by default — Arcjet asserts nothing about *human* approval, so the call proceeds through Eve's normal path.
- **vercel-eve-namespace.AC4.2 Success:** `policy.onAllow: "user-approval"` makes an ALLOW resolve to `"user-approval"` instead, so a site can require a human even when the policy passed. This is the knob for irreversible actions and is why ALLOW is not hardcoded.
- **vercel-eve-namespace.AC4.3 Failure:** On DENY the approval resolves to `{ type: "denied", reason }` where `reason` names the denying reason and, for `RATE_LIMIT`, the retry-after in seconds. The wrapped call does not execute.
- **vercel-eve-namespace.AC4.4 Success:** `guard()` is called with `label` = `policy.action`, the resolved rules, the session-derived `correlationId`, and metadata merged in order context ← policy ← per-call function, plus `eve.tool` (`ctx.toolName`) and `eve.call` (`ctx.callId`).
- **vercel-eve-namespace.AC4.5 Success:** `policy.rules` may be a static array or a function of the `ApprovalContext`, so a rate limit can be keyed on the session, the principal, or the tool input (`ctx.toolInput`).
- **vercel-eve-namespace.AC4.6 Failure:** With the default `onGuardError: "deny"`, **both** guard-unavailable signals — the guard call throwing, and a returned decision whose `hasFailedOpen()` is true — resolve to `{ type: "denied", reason }` naming an unavailable check, and capture `outcome: "unavailable"`. Not `"denied"`: a policy outage and a policy denial must stay distinguishable on the capture stream.
- **vercel-eve-namespace.AC4.7 Failure:** With `onGuardError: "allow"`, both signals resolve to `"not-applicable"` (or `policy.onAllow`) and emit a warning gated on `ARCJET_LOG_LEVEL`. The warning names the mode actually taken: the `"allow"` path's warning matches `/fail(ing|ed) open/` and the `"deny"` path's does not — it says "failing closed" or "was unavailable". The alternation is not laziness: `src/agents/guarded.ts` deliberately says "failing open" when the guard call threw and "failed open (API error)" when a decision reported itself failed-open, and this criterion asserts the *mode is named*, not one particular phrasing. A criterion demanding the literal `"failing open"` would be unsatisfiable against the second string while forbidding the fix.
- **vercel-eve-namespace.AC4.8 Success:** The gate captures exactly one event per evaluation, with `outcome` of `"allowed"`, `"denied"` or `"unavailable"`, and — for `guardApproval` specifically — metadata `eve.phase: "approval"`. The phase key is written by each helper, not by the shared `runGate` engine, which `guardInbound` also drives with `eve.phase: "inbound"`. It never captures `"success"` or `"error"` — the gate cannot observe execution, and claiming otherwise would make the capture stream lie. Execution outcomes come from `arcjetHooks` (AC6).
- **vercel-eve-namespace.AC4.9 Edge:** The returned function never throws, for any input, including a context missing `session`, a `rules` callback that throws, and a client whose `guard()` rejects. Eve treats a throwing approval as a failed call; a security helper must not be the reason a tool call fails.
- **vercel-eve-namespace.AC4.10 Success:** `policy.onDeny` reshapes the returned `ApprovalStatus`, and receives the `DecisionDeny`. It is **not** invoked on either unavailable signal.

### vercel-eve-namespace.AC5: `guardTool` wraps an authored tool, and `guardInbound` screens the channel

- **vercel-eve-namespace.AC5.1 Success:** `guardTool(client, tool, policy)` returns a definition that still carries Eve's tool brand (`Symbol.for("eve:tool-brand")`) **and** its definition-source key (`Symbol.for("eve.definition-source-key")`). The brand is enumerable and the source key is not, so a plain object spread silently drops the second one and breaks `toolResultFrom` matching in channel handlers. Both are asserted, including the source key's `enumerable: false` descriptor.
- **vercel-eve-namespace.AC5.2 Success:** The input definition is not mutated: `guardTool` returns a new object and the original's `execute` is unchanged by reference.
- **vercel-eve-namespace.AC5.3 Success:** On ALLOW the original `execute` runs with the same `(input, ctx)` it would have received, its result is returned unchanged, and the outcome is captured (`"success"`, or `"error"` with the original error rethrown unchanged).
- **vercel-eve-namespace.AC5.4 Failure:** On DENY, `execute` never runs. What the model receives is governed by `policy.onDeny`; the default throws `ArcjetDeniedError`, which Eve projects as a failed `action.result`. On either guard-unavailable signal under the default `onGuardError: "deny"`, `execute` also never runs and `ArcjetGuardUnavailableError` is thrown, with both discriminant legs distinguishable — `.cause` set and `.decision` reading `undefined` when the guard call threw, `.decision` set and `.cause` reading `undefined` when a decision failed open. Returning a denial *object* is not the default because an authored tool may declare an `outputSchema` that the object would violate — a `guardTool` that silently breaks a tool's declared contract is worse than a clean failure. A task in Phase 4 establishes empirically whether Eve validates tool output against `outputSchema`; if it does not, `policy.onDeny: "result"` becomes available as an opt-in.
- **vercel-eve-namespace.AC5.5 Success:** `guardTool` refuses to wrap a tool with no `execute` function, naming the problem.
- **vercel-eve-namespace.AC5.6 Success:** `guardInbound(client, text, options)` returns `{ allowed: true }` on ALLOW and, on DENY, `{ allowed: false, reason: "DENY", decision, message }` where `message` is a caller-presentable explanation and `decision` is the real decision so the caller can classify it further with a rule's own `results()`.
- **vercel-eve-namespace.AC5.7 Failure:** `guardInbound` maps both guard-unavailable signals to `{ allowed: false, reason: "UNAVAILABLE" }` under the default `onGuardError: "deny"`, and to `{ allowed: true }` with a gated warning matching `/fail(ing|ed) open/` under `"allow"` (see AC4.7 on why the phrasing is an alternation). This is the one helper whose `"allow"` mode is expected to see real use: a channel that fails closed on an Arcjet outage stops answering entirely.
- **vercel-eve-namespace.AC5.8 Success:** `guardInbound` never throws, and captures one event with `outcome` matching the verdict and metadata `eve.phase: "inbound"`.
- **vercel-eve-namespace.AC5.9 Success:** `guardInbound` accepts an explicit `correlationId` and uses it on both the guard and the capture payload. With it omitted, **no** id is generated and neither payload carries the key — an id nobody else knows looks like a correlation and joins to nothing. The channel boundary runs before a session exists, so there is no session id to derive from; the caller passes the identity it has (a thread or continuation token). AC6.3 is what makes the two halves joinable.

### vercel-eve-namespace.AC6: `arcjetHooks` captures the lifecycle

- **vercel-eve-namespace.AC6.1 Success:** `arcjetHooks(client, options?)` returns a `HookDefinition` whose `events` map is accepted by `defineHook` without a type error, and which contains only keys present in Eve's `HookEventMap`.
- **vercel-eve-namespace.AC6.2 Success:** An `action.result` event captures one event whose `outcome` is `"success"` for `status: "completed"`, `"error"` for `"failed"`, and `"denied"` for `"rejected"`, correlated by the session-derived correlation id and carrying `eve.phase: "result"`.
- **vercel-eve-namespace.AC6.3 Success:** A `session.started` event captures a join record carrying the session id and, when the hook context exposes one, `eve.continuation-token` and `eve.channel`. This is what lets a `guardInbound` decision correlated by thread token be joined to the in-session decisions correlated by session id.
- **vercel-eve-namespace.AC6.4 Success:** `subagent.called` captures a delegation record carrying the child session id, so a subagent's own Sequence can be reached from the parent's. `subagent.completed` captures a completion record carrying `callId` and `subagentName` **only** — its payload is `{ callId, output, subagentName }` and has no `childSessionId`, so the two events are joined to each other by call id rather than both naming the child session. (`output` is model-visible text and is never captured.)
- **vercel-eve-namespace.AC6.5 Edge:** Every handler is side-effect-only and never throws — including when the client's `capture()` throws and when an event's `data` is missing fields the handler reads. Eve's hooks are documented as observe-only; a throwing hook is a defect.
- **vercel-eve-namespace.AC6.6 Success:** `options.events` selects which event families are captured (`"session"`, `"turn"`, `"tool"`, `"subagent"`), defaulting to all four. An agent that runs long conversations must be able to bound capture volume.

## Glossary

- **Vercel Eve** — Vercel's filesystem-first framework for durable backend AI
  agents (`eve` on npm, `github.com/vercel/eve`). Capabilities are authored as
  files under `agent/`: `agent/tools/*.ts`, `agent/hooks/*.ts`,
  `agent/connections/*.ts`, `agent/channels/*.ts`. 0.31.0 as of 2026-08-06;
  pre-1.0. **Every Eve API claim in this document and in Phases 3–5 was verified
  against the `0.30.8` typings and must be re-confirmed against whatever version
  Phase 1 pins** — 0.31.0 landed during planning, which is itself the churn rate
  the peer range and the per-phase "verify against the installed typings"
  instructions exist for.
- **`defineTool`** — Eve's authoring helper for `agent/tools/*.ts`. Mutates the
  passed object to add an enumerable brand symbol and a non-enumerable
  definition-source key, then returns it. A tool's runtime *name* is its file
  slug, not a field.
- **`ToolContext`** — the second argument to an authored tool's `execute`.
  Extends `SessionContext` with `abortSignal`, `callId`, `toolName`,
  `getToken` and `requireAuth`.
- **`SessionContext`** — the runtime context shared by tools, hooks and channel
  events. Carries `session.id`, `session.auth`, `session.turn` and, for
  delegated subagent sessions, `session.parent` (with `rootSessionId`).
- **`approval`** — a field on an authored tool definition, an OpenAPI
  connection, and an MCP connection. A function of `ApprovalContext` returning
  an `ApprovalStatus`; `{ type: "denied", reason }` blocks the call and gives
  the model a reason. The widest enforcement point Eve exposes, and the only
  one that covers connection-derived tools.
- **`ApprovalStatus`** — `"not-applicable"` (no opinion; proceed),
  `"approved"`, `"denied"`, `"user-approval"` (ask a human), or the object
  forms carrying a `reason`.
- **Connection** — a declarative integration (`defineOpenAPIConnection`,
  `defineMcpClientConnection`) that surfaces remote operations as model-facing
  tools named `<connection>__<Operation>`. There is no local `execute` to wrap,
  which is why the approval gate matters.
- **Hook** — `agent/hooks/*.ts`, subscribing to runtime stream events under
  `events:`. Handlers return `void | Promise<void>`: **observe-only**, they
  cannot reject a turn or inject model context.
- **Channel** — `agent/channels/*.ts`, the inbound entry point (Slack, GitHub,
  Discord, HTTP…). A channel handler can decline to dispatch, making it the
  only place a turn can be stopped before it starts.
- **`action.result` / `ActionResultStatus`** — the stream event carrying one
  tool call's outcome, with status `"completed" | "failed" | "rejected"`.
  `"rejected"` is the approval-denied path.
- **Continuation token** — the identity a channel supplies to `agent.run()`;
  subsequent `deliver()` calls with the same token resume the same session. It
  is what a channel knows *before* a session id exists.
- **Sequence** — the Arcjet Console view reconstructing a run from every
  decision and capture event sharing one `correlationId` and site id.
- **`runGate`** — this namespace's own guard → capture engine for the approval
  path. Distinct from the agnostic `runGuarded` because an approval function
  never executes the call it gates, so there is no execution outcome to
  capture and `runGuarded`'s `execute` parameter has nothing to bind to.
- **Type-only import** — `import type { X } from "eve"`, erased at compile
  time. The namespace uses these exclusively so no test or consumer loads Eve
  unless they already depend on it.

## Architecture

### Layering (unchanged from the ADR)

| Path | Contains | SDK in its import graph |
|---|---|---|
| `@arcjet/guard` | client and rule builders | none |
| `@arcjet/guard/vercel-ai/v7` | `guardTool`, `aiToolsContext` + proxied agnostic layer | `ai` (runtime) |
| `@arcjet/guard/vercel-eve/v0` | `guardApproval`, `guardInbound`, `guardTool`, `arcjetHooks`, `eveAgentContext` + proxied agnostic layer | `eve` (**types only**) |

`src/agents/` stays internal with no export map entry. Both namespaces reach it
by `export * from "../../agents/index.ts"`, which is what makes AC1.2's
identity assertion meaningful for the first time: with two namespaces there
genuinely are two import paths that must yield one function.

### Why the surface differs from `vercel-ai/v7`

| `vercel-ai/v7` | `vercel-eve/v0` | Why |
|---|---|---|
| `aiToolsContext(ctx, tools)` fans a caller-made context across a `ToolSet` | *nothing* | There is no author-controlled `generateText` call to pass `toolsContext` to. Correlation is read from the session instead. |
| `createAgentContext({ correlationId })` at the call site | `eveAgentContext(ctx)` inside the callback | The durable session id already is the run identity; generating a second one would fragment the Sequence. |
| `guardTool` is the whole enforcement story | `guardApproval` is primary, `guardTool` secondary | Eve's model-facing tools often have no local `execute` (connections). `approval` covers tools *and* connections. |
| no inbound equivalent | `guardInbound` | Eve hooks cannot reject a turn; the channel handler is the only pre-turn gate. |
| capture rides on the wrapped `execute` | `arcjetHooks` on `action.result` | The approval gate cannot observe execution, so outcomes come from the event stream. |

### Contract: `@arcjet/guard/vercel-eve/v0`

```typescript
// Correlation, derived rather than generated.
function eveAgentContext(
  ctx: SessionContext,                       // a ToolContext, ApprovalContext or HookContext all satisfy this
  init?: { metadata?: ArcjetMetadata },
): ArcjetAgentContext;

// The primary gate. Assignable to an authored tool's `approval`, an OpenAPI
// connection's `approval`, and an MCP connection's `approval`.
function guardApproval<TInput = Record<string, unknown>>(
  client: ArcjetAgentClient,
  policy: GuardApprovalPolicy<TInput>,
): Approval<TInput>;

interface GuardApprovalPolicy<TInput> {
  action: string;                            // guard label + capture action, "resource.verb" past tense
  rules?: RuleWithInput[] | ((ctx: ApprovalContext<TInput>) => RuleWithInput[]);
  metadata?: ArcjetMetadata | ((ctx: ApprovalContext<TInput>) => ArcjetMetadata);
  onGuardError?: OnGuardError;               // default "deny"
  onAllow?: ApprovalStatus;                  // default "not-applicable"
  onDeny?: (decision: DecisionDeny) => ApprovalStatus;
}

// Authored tool files only: wraps `execute`, preserving Eve's brand and
// definition-source key.
function guardTool<TInput, TOutput>(
  client: ArcjetAgentClient,
  tool: ToolDefinition<TInput, TOutput>,
  policy: GuardToolPolicy<TInput>,
): ToolDefinition<TInput, TOutput>;

// The channel boundary — the only pre-turn gate Eve offers.
function guardInbound(
  client: ArcjetAgentClient,
  text: string,
  options: GuardInboundOptions,
): Promise<InboundVerdict>;

type InboundVerdict =
  | { allowed: true }
  | {
      allowed: false;
      reason: "DENY" | "UNAVAILABLE";
      message: string;                       // caller-presentable
      decision?: Decision;                   // present on DENY and on the failed-open signal
    };

// Observe-only capture. Mounted as `export default defineHook(arcjetHooks(client))`.
function arcjetHooks(
  client: ArcjetAgentClient,
  options?: { events?: ReadonlyArray<"session" | "turn" | "tool" | "subagent"> },
): HookDefinition;

// plus `export * from "../../agents/index.ts"`
```

### Correlation model

```
Slack message arrives
  └─ agent/channels/slack.ts
       guardInbound(aj, text, { correlationId: threadTs, rules: [injection, pii] })
       │   ← decision correlated by thread token
       ▼  (declines, or dispatches)
     eve session starts  ──────────────────────────────────────────────┐
       └─ agent/hooks/arcjet.ts  session.started                       │
            capture join record: correlationId = session.id,           │
              metadata { eve.continuation-token, eve.channel }  ───────┘  joins the two halves
       └─ model requests arcjet-internal__GetInternalRequestInfo
            approval: guardApproval(...)  ← decision correlated by session.id
            hooks: action.result          ← outcome correlated by session.id
       └─ subagent delegated
            correlationId = session.parent.rootSessionId  ← same Sequence
```

The join record exists because the channel handler genuinely cannot know the
session id: Eve creates the session *after* the handler returns, and the
handler's return type carries no identity back. Rather than pretend otherwise,
the design records the mapping once per session and documents that the console
join is two-hop for the inbound decision.

### Capture `outcome` vocabulary

| Emitted by | `outcome` | Meaning |
|---|---|---|
| `guardApproval` | `allowed` / `denied` / `unavailable` | the *gate* result; execution not yet attempted |
| `guardInbound` | `allowed` / `denied` / `unavailable` | the inbound screen result |
| `guardTool` | `success` / `error` / `denied` / `unavailable` | gate **and** execution, since it wraps `execute` |
| `arcjetHooks` | `success` / `error` / `denied` | execution outcome read from `action.result` status |

`allowed` is new. The existing values (`success`, `error`, `denied`,
`unavailable`) all describe an attempt to *do* the thing; a gate that passed has
not done it yet, and reusing `success` would make "the tool ran" and "the tool
was permitted to run" indistinguishable on the stream operators query. This
mirrors the reasoning that kept `unavailable` separate from `denied`.

### Shared changes to the agnostic layer

Two, both small and both tested.

**First**, the retry-after computation that
derives seconds from a rate-limit result's `resetAtUnixSeconds`, currently
inline in `src/vercel-ai/v7/guard-tool.ts`. `guardApproval`, `guardInbound` and
Eve's `guardTool` all need the identical calculation for their `reason` and
`message` strings, and three copies of a time-arithmetic edge case is how they
drift. It lands at `src/agents/denial.ts` with `vercel-ai/v7` retargeted onto
it and its behaviour re-asserted from the v7 tests unchanged.

**Second**, `createAgentContext`'s correlation-id validation predicate
(`correlationIdProblem`, private in `src/agents/context.ts`) is exported so
`eveAgentContext` can apply the same rule without inheriting the throw.
Duplicating the regex is the alternative and it is worse: the two definitions
would drift, and the whole point of AC3.3 is that Eve's derived id is checked by
*the same* rule that `createAgentContext` uses.

These are the two deliberate exceptions to the ADR's "adding a namespace
requires no shared-layer change". Both are extractions of existing tested
logic, not generalisations of a new abstraction, and both are scoped to Phase 2.
The ADR's claim survives in spirit — nothing about the layer's *shape* changed —
but it is now literally two edits rather than none, and saying "one" or "none"
would be wrong.

### Type-only coupling, concretely

`src/vercel-eve/v0/*.ts` may write:

```typescript
import type { ApprovalContext, ApprovalStatus, Approval, ToolDefinition } from "eve/tools";
import type { HookContext, HookDefinition } from "eve/hooks";
import type { SessionContext } from "eve/context";
```

and must not write `import { defineTool } from "eve/tools"`. Two consequences
fall out of that rule and both are load-bearing:

1. **`guardTool` cannot call `defineTool`.** It receives an already-branded
   definition and returns a copy built from
   `Object.getOwnPropertyDescriptors`, which is the only copy that preserves
   the non-enumerable definition-source key. A spread preserves the brand
   (enumerable) and silently drops the source key.
2. **`arcjetHooks` cannot call `defineHook`.** It returns a plain
   `HookDefinition` and the author wraps it:
   `export default defineHook(arcjetHooks(aj))`. `defineHook` is an
   identity-with-types helper, so this costs nothing at runtime.

### Naming: why `v0`

The ADR names the next namespace `vercel-eve/v1`. `eve` has published 144
versions across 30 minor lines (0.2 → 0.31) and has never published a 1.x on
any dist-tag. Under semver a 0.x minor may break, so `v1` would be a version
segment that names nothing, inside a convention whose entire purpose is to make
the SDK major explicit and greppable. The path is `vercel-eve/v0` with the peer
pinned `>=0.30 <1`; `vercel-eve/v1` is added additively when Eve reaches 1.0,
exactly as `vercel-ai/v8` would be. The ADR is corrected as part of this work
rather than left to contradict the code.

## Existing Patterns

**Followed:**

- **Namespace layout** (`arcjet-guard/src/vercel-ai/v7/`): one directory per
  `<vendor-sdk>/v<major>`, a barrel `index.ts` that adds its own exports and
  proxies `../../agents/index.ts`, and co-located `*.test.ts` importing
  **source** with `./foo.ts` specifiers.
- **Build config**: `arcjet-guard/tsdown.config.ts` globs
  `src/**/*.ts` with `unbundle: true`, so `src/vercel-eve/v0/` emits to
  `dist/vercel-eve/v0/` with no config change.
- **Export map**: two-segment literal keys, no wildcard, no unversioned alias;
  strict `exports` encapsulation is what makes AC1.3 pass without build-time
  machinery.
- **Optional peers**: `peerDependencies` + `peerDependenciesMeta.*.optional`,
  as `ai` and `@ai-sdk/provider-utils` already are.
- **Fail-closed default**: `onGuardError` defaults to `"deny"` on every
  enforcing helper, per
  [2026-07-27: fail closed by default](../../../arcjet/docs/adrs/2026-07-27-sdk-agent-helpers-fail-closed-default.md).
- **Warning gate**: `shouldWarn()` reading `ARCJET_LOG_LEVEL`, with constant
  format strings and interpolated arguments (the Semgrep requirement) —
  `src/agents/guarded.ts` is the reference.
- **Static source scans**: `test/_shared/source-scan.ts` already provides
  `collectTsFiles` and `extractImportSpecifiers`; AC2.1's type-only check
  extends the same pattern rather than inventing a second one.
- **Stub client**: `test/_shared/stub-client.ts` for recording `guard()` and
  `capture()` calls.

**New patterns introduced:**

- **A type-only vendor namespace.** `vercel-ai/v7` imports `ai` at runtime
  (`jsonSchema`). This one imports nothing, which is a stricter posture the
  test suite has to enforce deliberately (AC2.1) because nothing else would
  catch a value import creeping in.
- **A namespace-local engine.** `runGate` in `src/vercel-eve/v0/gate.ts`, next
  to but not inside the agnostic `runGuarded`. The ADR anticipated this: a
  helper the shared layer cannot express lives in the namespace.
- **A capture-only integration surface.** `arcjetHooks` is the first helper
  that enforces nothing at all. Its value is entirely the Sequence.

## Additional Considerations

**The `v0` naming decision is reversible in the cheap direction.** Adding
`vercel-eve/v1` when Eve GAs is additive. Had we shipped `v1` now and Eve's 1.0
broken the surface, the only honest fixes would have been a breaking change to a
published path or a `v2` that skips a major nobody integrated.

**Eve's Node 24 floor is a consumer-facing constraint, not just ours.** An
agent using this namespace is already on Node 24 because Eve requires it. What
the type-only rule protects is `@arcjet/guard`'s own matrix and every consumer
who installs guard without Eve. The README states the floor so nobody reads
`>=22.21.0` on the package and assumes the namespace works there.

**Capture volume.** `arcjetHooks` on a long conversation emits an event per tool
call plus per turn. `options.events` bounds it, and the skill should recommend
starting with `["session", "tool"]` for chatty agents. This is the first helper
whose cost scales with conversation length rather than with call sites.

**The inbound join is two-hop and that is a real cost.** A channel decision
correlated by thread token and in-session decisions correlated by session id are
joined through the `session.started` record. If a future Eve release hands the
session id back to the channel handler — or exposes the continuation token in
`SessionContext` rather than only `HookContext` — this collapses to one hop and
`guardInbound`'s explicit `correlationId` becomes optional. Worth re-checking at
each minor.

**No sandbox enforcement point has been found.** `eve/sandbox`'s
`defineSandbox` exposes `bootstrap` and `onSession`, which run outside the
ALS-scoped context and receive domain-specific arguments rather than a
`SessionContext`. Guarding an individual sandbox command would need a hook Eve
does not currently offer. The `guard-sdk-namespaces` design listed sandbox
command execution as an Eve guard surface; this investigation does not support
that, and the claim should not be carried forward unexamined.

**An Eve extension is the natural next step and is deliberately not this
work.** `defineExtension` lets a package ship tools, hooks and connections that
an agent mounts with one line, which would reduce the integration to
`export { default } from "@arcjet/eve-extension"`. It is a separate package with
its own release cadence, it cannot be a subpath of `@arcjet/guard` (extensions
are mounted by path convention, not imported), and it should be designed once
this namespace has real usage behind it.

**This namespace is the evidence the ADR asked for.** The ADR deferred whether
the agnostic layer gets promoted to the root export until a second vendor
namespace existed. It now does, and the answer this design supports is yes: the
agnostic surface came across unchanged apart from two small extractions, and
`guardInbound` is a genuinely non-AI call site (a webhook handler) that today
must import a vendor path to reach `guardAction`. Making that change is a
follow-up with its own ADR, not a phase here.

**Version churn risk is higher than for `vercel-ai/v7`.** Eve shipped 30 minor
lines in under a year — one of them, 0.31.0, during the writing of this plan —
and this namespace touches `ToolDefinition`,
`ApprovalContext`, `ApprovalStatus`, `SessionContext`, `HookEventMap` and two
brand symbols. All are type-level except the brands. The renovate/dependabot
bump for `eve` should be treated as a review-required change rather than an
automerge, and the typecheck is what catches most of it.
